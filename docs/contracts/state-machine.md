# 订单与拼团状态机 v1

日期：2026-10-24。沿用现有数据库编码，避免改枚举破坏既有前端。

## 订单状态

| 值 | 含义 | 允许的后续状态 |
| --- | --- | --- |
| 1 | 待付款 PENDING_PAYMENT | 模拟支付至 2；用户取消至 6 |
| 2 | 待接单/待履约 TO_BE_CONFIRMED | 管理员接单至 3；允许取消至 6；已付款自提核销至 5 |
| 3 | 已接单 CONFIRMED | 配送至 4；已付款自提核销至 5；管理员取消规则待实现 |
| 4 | 配送中 DELIVERY_IN_PROGRESS | 管理员确认送达至 5 |
| 5 | 已完成 COMPLETED | 终态，重复支付不得改回 2，不得取消 |
| 6 | 已取消 CANCELLED | 终态，禁止重新支付或核销 |

订单的 `payStatus` 独立：0 未付款，1 已付款，2 模拟退款。`verifyStatus` 独立：0 未核销，1 已核销。配送单和自提单由履约信息区分，不增加与旧编码冲突的状态值。

模拟支付只能把本人 `status=1,payStatus=0` 的订单推进到 `status=2,payStatus=1`。已付款且处于有效状态时重试返回已有结果，不改变 checkoutTime 或已完成状态。退款、取消、非法组合必须拒绝。

用户取消仅允许 1 或 2；重复取消可幂等返回。已付款取消仅记录模拟退款，不调用真实微信退款。库存回补必须与首次成功的取消状态迁移在同一事务完成；完整实现仍需后续任务证明。

自提核销必须同时满足：存在自提点、已付款、状态为 2 或 3、未核销、若为团购则已经成团。条件更新只允许一次成功，置 `status=5,verifyStatus=1,verifyTime=now`。不能只检查码存在。

管理员身份从管理员 JWT 获取，用户入口仅能处理本人订单。管理员详情与本人详情应显式分开，不能通过“数字 ID 恰好相同”推断角色。

## 拼团状态

| 值 | 含义 | 后续状态 |
| --- | --- | --- |
| 1 | 进行中 IN_PROGRESS | 人数满足且未过期 → 2；失败 → 3；到期 → 4 |
| 2 | 成功 SUCCESS | 终态，关联已付款订单可履约 |
| 3 | 失败 FAILED | 终态，释放库存并记录模拟退款 |
| 4 | 已过期 EXPIRED | 终态，释放库存并记录模拟退款 |

保留现有“开团/参团时建立订单和成员关系”的模型。计划在参团后、成团前允许模拟支付；人数表示成员数，资金状态由关联订单单独表达。成团不自动把未付款订单写成已付款。到期关团要与订单取消、库存回补、退款记录一起完成并支持重试；这部分为待验证/待修复目标。

过期判断以服务端 Asia/Shanghai 时间为准。并发参团、同用户重复参团、成团与过期竞争都需数据库条件更新和事务保障。
