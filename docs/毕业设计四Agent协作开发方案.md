# 社区团购与生鲜配送系统毕业设计协作方案

版本：V2，2026-10-24。用途：开发前范围确认与四个 agent 的任务分派。替代原三 Agent 方案。

建议在现有项目上补齐真实业务闭环，保留 Spring Boot 2.7 多模块后端和 uni-app 用户端。Antigravity Gemini 负责用户小程序，GLM 负责管理与履约前端，Codex 负责后端、数据库、接口契约与集成，DeepSeek Harness（DeepSeek 4.1 Flash）负责独立测试、接口核验与毕设验收材料。先完成可重复演示的毕设核心，再考虑扩展营销功能。

本方案基于课题大纲正文及本地源码静态检查；未启动数据库、后端或微信开发者工具，未进行编译和真机测试，不把“存在文件”当作“功能已完成”。本轮只新增方案，不实施业务改动或推送 GitHub。

## 1 毕设要求及范围

目录中的《杨雪--基于微信小程序的社区团购与生鲜配送系统设计与实现.docm》是一份课题大纲，并非完整论文或详细验收表。

明确要求包括：

- 微信小程序；具备页面生命周期、组件、事件处理、本地缓存等实现。
- 生鲜商品上架展示、团购下单购买。
- 订单状态跟踪、收货地址维护。
- 商品销量、团购订单等历史数据统计分析。
- 保存用户下单与消费记录。
- 交付可运行程序、源代码、论文。

大纲未明确要求真实微信支付、真实短信、独立骑手端、AI 客服、提现、积分、秒杀、多商户结算，也没有指定四端架构。既有页面不自动成为必须交付的需求。

建议采用以下业务范围：

| 级别 | 范围 | 验收原则 |
| --- | --- | --- |
| 必须 | 用户小程序、商品管理、团购、订单、地址、消费记录、销量与团购统计 | 全部有真实数据库读写和操作证据 |
| 必须 | 基础履约：送货上门与社区自提 | 建议双模式；上门配送采用管理员更新状态，无需另做骑手端 |
| 必须 | 平台管理后台 | 商品上下架、订单处理、团购管理、基础统计 |
| 优先复用 | 自提点选择、提货码、核销 | 保留已有能力，补状态及权限校验 |
| 扩展 | 独立商家端、自提点端 | 在核心闭环通过后扩展，时间不足可将基础操作放入管理后台 |
| 暂缓 | AI 客服、邀请现金、提现、免费领、复杂优惠券及积分 | 不纳入第一版验收，不让半成品入口影响演示 |

“配送”与“团购”的具体含义需要在开工阶段向导师核对。当前默认保留已有开团/参团模型，并增加最小送货上门流程；这属于建议设计，不声称是大纲逐字规定。若导师认可集中采购加社区自提，可缩减配送流程，但地址管理仍应保留。

### 2.1 已确认的优先问题

1. **文档与工程不一致。** 根 README 写 Boot 3、`com/fresh`、3001 及其他旧目录，实际为 Boot 2.7.3、`com/sky` 多模块，后端配置端口为 8080。部署文件也引用旧的 jar 路径。
2. **各端服务地址不统一。** 用户端开发地址为 8080，管理、商家、自提点端仍指向 3001；冒烟脚本默认也是 3001。
3. **正常业务中混入示例数据。** `ApiOrderController` 在订单列表为空或详情读取失败时生成示例订单，甚至含手机商品；`ApiPayController` 对不存在订单生成提货码。必须改成真实空列表、明确失败，演示种子数据单独入库。
4. **订单直接提交路径信任客户端价格。** `ApiOrderController.submitOrder` 接收前端 amount 和明细价格直接落库，缺失金额还使用固定兜底值。应统一由服务层查询商品、计价、校验并事务落库。
5. **订单归属保护不足。** 当前详情、取消、模拟支付路径未看到完整的当前用户归属校验；取消还吞异常返回成功。需加入跨用户访问和非法状态测试。
6. **评价存在假成功。** `ApiDishController` 返回固定评价，提交评价只记录日志后返回成功。第一版应隐藏该扩展入口或实现持久化，不能写进已完成功能。
7. **密码设置路由与拦截规则冲突。** 拦截器排除了整个 `/api/auth/**`，而 `/api/auth/set-password` 依赖拦截器设置当前用户。需要区分公开登录接口和需要登录的账户操作。
8. **配置与日志需整理。** 发现地图配置直接写在源码、JWT 校验记录完整 token。发布前改为适当配置管理与日志脱敏，并检查已入库的凭据；不要在报告或 PR 贴出密钥值。

成功码不是已确认故障：`Result.success` 虽返回 1，但 `ResultResponseAdvice` 已把 `/api/**` 转换为 200。开发时保留这一兼容事实，避免只改通用返回类破坏旧接口。需要统一接口契约和测试，而非盲目全局替换。

## 3 四个 Agent 的目录分工

分工依据是模块边界和修改冲突，不对用户所列模型作未经验证的性能排名。以下 Gemini、GLM、DeepSeek 指用户实际使用的工具与配置。第四位独立验证业务结果，避免让同一个实现者成为唯一验收者；不增加一套重复后端。

| 负责人 | 唯一主责目录 | 工作内容 | 交付证据 |
| --- | --- | --- | --- |
| Antigravity Gemini 3.8 Flash | `front/`、`docs/agents/gemini/` | 用户小程序交互、页面、请求适配、地址与团购页面、小程序构建与真机适配 | 用户端 PR、构建日志、操作截图、联调说明 |
| GLM 5.3 / FLASH | `front-admin/`、`front-merchant/`、`front-partner/`、`docs/agents/glm/` | 优先管理后台：商品、团购、订单履约、统计；核心通过后再补独立商家/自提点端 | 管理端 PR、真实数据统计截图、履约与核销录像或步骤 |
| Codex | `backEnd/`、`deploy/`、`scripts/`、`tools/`、`.github/`、根 README、根 `.gitignore`、公共 `docs/`（下列专属目录除外） | 接口与数据模型、认证权限、订单事务与团购、统计、迁移、后端单元及集成测试、部署、PR 集成 | 后端 PR、契约、迁移及初始化说明、测试记录、发布清单 |
| DeepSeek Harness / DeepSeek 4.1 Flash | `tests/acceptance/`、`docs/qa/`、`docs/thesis/`、`docs/agents/deepseek/` | 外部 API 契约测试、跨端业务验收、异常与越权测试、报表对账、缺陷复测、论文素材与答辩流程 | 测试代码 PR、缺陷清单、带版本信息的验收报告、论文素材与演示脚本 |

公共文件由 Codex 维护，各 `docs/agents/<负责人>/` 由本人维护，`docs/qa/` 与 `docs/thesis/` 由 DeepSeek 维护。前端依赖和锁文件由对应前端负责人维护。DeepSeek 的测试运行器配置和测试依赖放在 `tests/acceptance/`，由 Codex 将其接入 CI。跨目录修改先交由该目录负责人处理，不允许其他 agent 顺手改数据库、后端接口或他人请求封装。历史 `backEnd/WeiXinApp/`、`backEnd/Web/` 暂作参考，评估后再决定是否移出交付目录，不直接删除。

### 3.1 Gemini 任务包

- G1：验证 H5 和 mp-weixin 构建；核对页面、图片及 API 地址，提供可复现启动说明。
- G2：完善商品分类、搜索、详情、购物车、个人中心；补加载、空数据、断网、登录失效状态。
- G3：新增地址列表、添加、编辑、删除、默认地址；结算选择地址或自提点，地址与门店不可混用。
- G4：接入团购商品、开团、参团、团详情、我的团购；显示真实成团人数、截止时间和失败状态。
- G5：接通下单、模拟支付、取消、订单记录、配送状态、自提码；只显示后端返回的真实状态和金额。
- G6：微信开发者工具和真机验收；验证缓存恢复、页面返回刷新、网络失败、地址切换和重复点击。

完成标准：用户在微信小程序中从浏览到履约完成的主流程可重复操作；刷新和重新登录后记录一致；无前端伪造成功、假订单或硬编码金额。

### 3.2 GLM 任务包

- L1：管理后台构建与登录，按冻结契约替换不存在的接口调用，明确无权限和登录失效状态。
- L2：商品分类、商品新增/编辑、上下架、库存维护；不要只做只读列表。
- L3：团购活动配置及订单查询；配送订单处理、到货和自提核销。基础操作先在管理后台闭环。
- L4：销量榜、营业额趋势、订单趋势、团购成功/失败统计，支持日期筛选；展示明确统计口径。
- L5：用后端种子数据核对报表，提供手工可计算的对照结果。
- L6：核心验收通过且时间允许时，再接通商家商品/备货和自提点到货/核销；否则关闭未实现入口。

完成标准：后台操作能改变用户端实际可见结果；统计来自真实订单；同一自提码重复核销不产生第二次履约；各角色看不到无权操作的数据。

### 3.3 Codex 任务包

- C1：核实运行基线，统一配置说明，建立需求对照表、接口清单和最小角色矩阵。
- C2：冻结请求/响应、分页、时间、金额、ID、错误码、角色和状态契约；决定新端复用旧接口还是新增薄适配层，核心 service 保持一份。
- C3：修复登录与受保护账户操作、订单归属及管理员权限；移除正常链路中的示例兜底和吞异常成功。
- C4：重构统一下单服务，服务端计价、库存条件扣减、事务回滚、幂等提交、状态迁移、取消回补与核销。
- C5：检查团购开团/参团并发、重复参团、成团与订单关联、到期失败、库存释放与支付处置。
- C6：补地址/履约/统计契约与必要接口；添加最小可解释的团购统计，复用已有销量和营业额实现。
- C7：整理数据库初始化、种子数据和增量迁移，编写后端单元及集成测试；为 DeepSeek 提供隔离测试环境和可复算种子数据。
- C8：更新启动/部署文档和脚本、配置 CI、审查其他三位 agent 的 PR；依据 DeepSeek 独立验收结果组织修复与发布，复核论文材料中的技术事实。

完成标准：从干净克隆及空数据库按文档运行；所有核心操作可追溯到数据库；异常及权限测试通过；不存在重复扣库存、重复履约或非法跨用户操作。

### 3.4 DeepSeek 任务包

- D1：从本方案要求建立需求—页面—接口—测试用例对应表，核对现有路由、配置与文档；区分已确认缺陷、待验证风险和范围外功能。
- D2：根据冻结契约在 `tests/acceptance/` 编写可重复运行的 API 验收脚本，覆盖登录、地址、商品、团购、订单、支付、履约与统计，不复制后端业务实现充当预期结果。
- D3：重点验证篡改金额、负数量、库存不足、重复下单、重复参团、超时失败、跨用户查单/取消/支付、重复核销。并发和数据重置只能在隔离测试库执行。
- D4：按 A01–A14 完成跨端验收和报表对账；微信真机由 Gemini 提供执行证据，DeepSeek复核版本、步骤与结果。没有设备或环境时记录“未验证/阻塞”，不据截图推断全部通过。
- D5：维护 `docs/qa/bugs.md`，每项写明优先级、提交 SHA、环境、前置数据、复现步骤、预期/实际结果、责任人、修复 PR 和复测结论。前端缺陷交对应负责人，后端缺陷交 Codex。
- D6：在 `docs/thesis/` 整理真实实现对应的需求分析、测试章节素材、截图索引、操作手册和答辩演示脚本；架构、ER、接口事实由 Codex复核，页面说明由各前端负责人复核。
- D7：对候选发布提交生成验收报告，列出通过、失败、未执行、阻塞项；失败项修复后复测，不能为让测试通过而降低断言或自行修改契约。

完成标准：测试脚本和文档均通过独立 PR 提交；验收证据可对应到确定提交及测试数据；核心用例全部通过才建议发布。未实现功能、未执行测试和模拟支付都明确标注。DeepSeek 不直接修改业务代码、生产配置、迁移或 CI，发现问题交对应目录负责人修复。

## 4 并行开发前冻结的契约

由 Codex 先提交 `docs/contracts/api-v1.md` 和 `docs/contracts/state-machine.md`，Gemini 与 GLM 据此开发，DeepSeek 据此设计验收测试。契约尚未冻结时，DeepSeek 先做需求映射、已有问题复现和用例设计，不虚构端点。

- 用户、管理员为首期角色；启用独立商家与自提点端时再增加受约束角色，不用普通用户 token 充当运营权限。
- 列出前端实际使用的接口：地址、商品、团购、订单、履约、报表；逐条注明已实现/待实现和负责人。
- 保留旧 `/user/**`、`/admin/**` 与新 `/api/**` 的成功码区别，前端在请求层适配，页面只处理规范化结果。
- 冻结分页字段，避免 `records/list`、`page/pageNum` 混用；大整数 ID 使用字符串传输。
- 金额由后端以 BigDecimal 计算，明确单位和精度；前端金额仅用于展示，不能作为成交依据。
- 明确时区 Asia/Shanghai、截止时间、配送日期、展示格式与时间戳单位。
- 订单状态建议区分待付款、待履约、配送中/待自提、已完成、已取消；团购状态另设进行中、成功、失败，不能混在一个枚举里。
- 明确参团付款时点、成团后订单关系、未成团资金处置；模拟支付可记录模拟退款，但不得声称真实退款已完成。
- 定义重复请求、库存不足、失效团购、不存在订单、越权访问、重复核销的确定行为。
- 契约变更先更新文档、给出影响端和兼容办法，再提交实现；不要让两个前端猜后端字段。

前端可在独立开发模式使用标明为 mock 的样例调试 UI，但联调和验收必须切换到真实后端，业务失败不能自动回退假成功。

## 5 建议排期与依赖

暂按约 12–15 个有效工作日安排，属于工作量预估，并非已知截止日期；每日进度按验收结果调整。增加第四位主要用于提前发现缺陷、并行产出材料，不直接按人数比例缩短工期。真实支付、商家结算和复杂营销不包含在此估算内。

| 阶段 | 时间建议 | Gemini | GLM | Codex | DeepSeek | 阶段验收 |
| --- | --- | --- | --- | --- | --- | --- |
| M0 基线和范围 | 第 1–2 日 | 验证用户端构建及缺页 | 验证后台构建、列接口缺口 | 运行后端/数据库、冻结契约与数据模型 | 需求映射、缺陷复现、用例设计 | 各端启动方式明确，契约可评审 |
| M1 核心开发 | 第 3–6 日 | 地址、团购、订单页面 | 商品、团购、订单后台 | 认证、交易、库存、团购、迁移 | API 脚本、逐模块验证、缺陷登记 | 商品到下单真实入库；地址和团购可操作 |
| M2 履约和统计 | 第 7–9 日 | 配送/自提展示及消费记录 | 履约、核销、统计 | 状态迁移、权限、报表与内部测试 | 跨端验收、越权及并发测试、统计对账 | 下单到完成闭环；统计可复算 |
| M3 集成修复 | 第 10–12 日 | 微信端兼容和交互修复 | 后台异常与权限修复 | 集成、CI、缺陷修复、部署 | 干净环境验证、回归及真机证据复核 | 干净环境可复现；核心回归通过 |
| M4 毕设交付 | 第 13–15 日 | 用户操作截图与说明 | 管理操作截图与报表证据 | 技术事实复核、发布包 | 验收报告、论文素材、操作及答辩脚本 | 程序、源码、论文素材一致 |

顺序：M0 契约通过 → 四方并行 → 每个业务模块小步合并并独立验证 → M2 闭环 → M3 集成验收 → M4 冻结版本。DeepSeek 从第一阶段介入，不等待其他三位全部写完才开始测试。

如时间压缩，优先保留用户小程序、管理后台、真实团购、地址、基础配送/自提、统计；独立商家和自提点前端排后。没有真实微信商户资格时使用明确标识的模拟支付，不让第三方接入阻断主体毕业设计。

## 6 GitHub 协作与提交规则

目标沿用已配置的 origin 仓库。开工前先核对远端分支、权限、当前基线；本方案没有创建分支或执行推送。

1. 四个 agent 使用独立 clone 目录或独立 worktree，不在同一个工作目录同时切分支。
2. 建议采用 `main` 稳定分支、`develop` 集成分支、每任务独立分支；由 Codex 负责集成。
3. 分支示例：`feat/gemini-address`、`feat/glm-admin-orders`、`feat/codex-order-service`、`test/deepseek-order-acceptance`、`docs/deepseek-thesis-materials`。每完成一个可验证模块就 push 并建 PR 到 develop，DeepSeek 同样提交测试代码和文档，而非仅在聊天里报告。
4. 共享契约和基础迁移先合入 develop，各 agent 更新基线后再实现依赖模块。
5. 每个 PR 写清功能、修改目录、依赖接口/迁移、测试命令与结果、截图、已知限制；不能把“没运行”写为“通过”。
6. 涉及已有数据的 SQL 必须用增量迁移；数据库脚本只由 Codex 修改。初始化脚本和测试重置脚本明确区分。
7. 未经协调不 force push，不覆盖别人提交；合并冲突由修改文件的负责人处理，Codex复核跨模块影响。
8. CI 应覆盖后端编译与测试、用户端 H5/小程序构建、管理端构建；微信真机和数据库全链路另留人工证据。扩展端启用后加入相应验证。
9. 业务负责人完成自测后提交 PR，Codex 负责代码与集成审查，DeepSeek 对相应功能独立验证。合并后按登录→浏览→地址/自提点→开团或下单→支付→履约→统计检查；DeepSeek 的验收报告必须对应最终候选提交，develop 全部通过后再发 release PR 到 main。
10. 最终版本打标签，例如 `v1.0.0-graduation`；记录提交 SHA、初始化方法和演示步骤，保证论文截图对应同一版本。

禁止提交 node_modules、target、dist、日志、真实用户数据和私有凭据。已有追踪文件不能仅靠 `.gitignore` 解决；确认泄露的秘密应撤换并清理配置，历史重写需单独评估。课题原文含教师联系方式，默认不上传；仓库仅保留不含联系方式的需求摘要。

## 7 必须通过的验收用例

DeepSeek 维护验收结果，各模块负责人负责自测与修复；Codex 的内部测试和 DeepSeek 的外部验收互补，不重复维护同一测试文件。环境或设备缺失时保留未执行状态并注明依赖。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| A01 | 空数据库初始化、启动各端 | 按文档复现，无手工猜表或补字段 |
| A02 | 新用户登录并维护地址 | 默认地址正确、用户之间隔离、重登后保留 |
| A03 | 后台上下架商品及调整库存 | 用户端展示和可购买状态同步 |
| A04 | 开团、第二用户参团、成团 | 人数、订单、库存及团购状态一致 |
| A05 | 团购超时或重复参团 | 失败处理和库存释放正确，不重复计数 |
| A06 | 修改客户端价格、负数量、超库存下单 | 后端拒绝非法参数或使用服务端正确价格 |
| A07 | 重复提交和并发购买最后库存 | 不重复创建有效订单、不超卖、不扣成负数 |
| A08 | 空订单列表、无效订单号、他人订单号 | 返回真实空数据或明确错误，不返回演示订单 |
| A09 | 模拟支付、重复支付、取消后支付 | 状态正确且幂等；不存在订单不能生成提货码 |
| A10 | 配送状态推进或到店核销 | 非法跳转拒绝，重复核销无额外效果 |
| A11 | 用户/运营/其他门店越权操作 | 服务端拒绝，不能只靠页面隐藏按钮 |
| A12 | 统计对账 | 指定种子订单可复算销量、营业额和团购统计 |
| A13 | 小程序真机和缓存恢复 | 可联网、图片显示正常、登录/购物车缓存合理、刷新后订单一致 |
| A14 | 程序重启 | 历史订单和消费记录保留，不依赖内存假数据 |

## 8 毕设材料同步产出

DeepSeek 负责汇总论文素材、需求对应表、测试报告、操作说明和答辩脚本；Codex 提供并复核总体架构、ER 图、接口与状态设计、数据库字典、部署事实及局限。Gemini 提供用户页面与小程序机制说明；GLM 提供后台操作、履约和统计说明。截图和数据记录来源提交，不把计划描述写成实现结果。

论文建议章节：绪论、相关技术、需求分析、系统设计、系统实现、系统测试、总结展望。具体格式、字数、引用标准与提交时间以学院另发要求为准，当前大纲未提供。学生需理解并能演示核心代码，核对论文描述、数据和运行结果；不得把未实现的扩展功能写为已完成。

## 9 可直接交给 Agent 的启动指令

### 发给 Antigravity Gemini

请先阅读 `docs/毕业设计四Agent协作开发方案.md` 和已冻结的 `docs/contracts/` 契约。你负责 `front/` 和 `docs/agents/gemini/`，在独立工作目录及 feature 分支工作。先验证 H5/微信构建，再补地址管理、开团参团、订单和配送/自提页面，最后做真机与异常场景验收。依赖接口未确定时先登记问题并完成不依赖接口的页面工作，不自行修改后端或猜字段。每个可验收模块分别提交 PR，附真实测试记录和供 DeepSeek 复核的真机证据；验收禁止伪造订单或成功状态。GitHub 基线和权限确认后再推送你的功能分支。

### 发给 GLM

请先阅读 `docs/毕业设计四Agent协作开发方案.md` 和已冻结的 `docs/contracts/` 契约。你负责 `front-admin/`、`front-merchant/`、`front-partner/` 和 `docs/agents/glm/`，在独立工作目录及 feature 分支工作。优先把管理后台的登录、商品、团购、订单履约和统计接通真实后端，基础核销先在后台完成；独立商家/自提点端在核心闭环通过后再扩展。不得自行修改后端、数据库或用户端。逐模块提交 PR，附构建结果、真实数据截图、报表口径和对账证据，并处理 DeepSeek 复测发现的本端问题。GitHub 基线和权限确认后再推送你的功能分支。

### 给 Codex 的后续执行指令

按 `docs/毕业设计四Agent协作开发方案.md` 执行后端和集成任务。先验证运行环境、数据初始化和现有接口，冻结契约、角色矩阵及状态机，再修复示例订单兜底、服务端计价、归属权限、事务库存、团购和履约统计。维护公共文档、迁移、后端内部测试和部署，为 DeepSeek 提供隔离测试环境并接入验收脚本；不直接修改其他 agent 主责目录，跨目录需求交给相应负责人。核对 GitHub 基线和权限后按任务提交 PR，审查并集成各端改动，根据独立验收报告修复问题并发布。

### 发给 DeepSeek Harness（DeepSeek 4.1 Flash）

请先阅读 `docs/毕业设计四Agent协作开发方案.md`。你负责独立测试与毕设验收材料，拥有 `tests/acceptance/`、`docs/qa/`、`docs/thesis/`、`docs/agents/deepseek/` 的修改权，在独立工作目录及任务分支工作。先建立需求映射和用例清单、复现已有问题；契约冻结后实现可重复运行的 API 测试，重点检查价格篡改、库存并发、重复操作、订单归属、团购到期、核销和报表对账。只在隔离测试环境执行写入、并发及重置操作。发现缺陷登记复现步骤、版本、预期/实际和责任人，交对应开发者修复，不改业务代码或降低断言。配合 Gemini 复核微信真机证据，逐步整理真实的论文素材、测试报告及答辩流程。测试代码和文档均提交 PR，结果明确区分通过、失败、未执行与阻塞；核对 GitHub 基线和权限后推送自己的分支。最终验收报告必须对应候选发布提交，不虚构测试结果或截图。
